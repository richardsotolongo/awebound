# AGENTS.md — apps/web

The whole site: Next.js 16 App Router. Server Components read the catalog directly from server code; Client Components handle interaction and call Server Actions. Brand rules live in `packages/brand/AGENTS.md` and the `awebound-brand` skill: read them before visual work.

## Conventions

- **Catalog data** lives in Supabase: `collections` (releases, draft or published), `pieces` (draft, `in_review` = approved and waiting for its release, published) and `size_guides`. The public reads them with the publishable key and no session, so row-level security returns only published releases, their published pieces and the guides those use (column grants keep `blank` and import paths out). `getBrandContent()` caches the rows for a minute under the `catalog-content` tag (Next's data cache, like Fourthwall's list) and falls back to `catalog.json` when the database isn't set up or can't be read (the Health page says which). A piece that doesn't hold together (unknown category, a price for a size its guide lacks) is left out and logged; the owner's forms run the same check before saving. Categories and garment color tokens stay in `catalog.json`. Every owner change that shoppers can see calls `refreshPublicPages()`, so it shows at once.
- **Data**: Server Components call `server/catalog.ts` directly, wrapped in `withFallback` so a Fourthwall outage renders an empty state instead of crashing. Fourthwall's product list is fetched with `next: { revalidate: 60, tags: ["fourthwall-catalog"] }` (the webhook's product and collection events refresh that tag at once), so About and the sitemap stay static and refresh every minute. The home page renders per visit (its My Archive section knows who is signed in) and always opens on the release's primary piece; its catalog reads still come from that one-minute cache. Product pages are cached the same way but render on their first visit (`revalidate` plus an empty `generateStaticParams`), so a deploy never depends on Fourthwall. Don't add `no-store` on the catalog path.
- **Server Actions** (`server/actions.ts`) are the only way the browser reaches the server. Each one parses its input with a schema from `shared/`, reads the user from the Supabase session, and returns `Result<T>`: `{ ok: true, data }` or `{ ok: false, error, fields? }`. Next hides thrown messages in production, so never rely on a thrown error reaching the client; throw `UserError` for messages the shopper should see.
- **Secrets** stay in `server/` and `lib/supabase/admin.ts` (`import "server-only"`). Brand content is server-only too, so the catalog JSON never ships to the browser.
- **Shop state lives in the URL** (`collection`, `category`, `q`, `color`, `size`, `minPrice`, `maxPrice`, `sort`). No `collection` (or `all`) means All collections, the default; `latest` still resolves to Latest Drop (the newest release, from `CatalogIndex.releases()`), and on All collections the shop's header promotes it. The toolbar's selects, in order after a short search box (Collection, always shown: All collections, then each release; Category; Sort), and the sheet's filters all use `useCatalogState()`, which updates optimistically and replaces the URL in a transition. `shopHref`/`shopCanonical` build shop links elsewhere.
- **Scripture**: never hard-code a verse in a component. Products carry `scripture` (a `ScriptureQuote` resolved on the server); site verses come from `VERSES` in `server/scripture.ts`. Render with the brand `ScriptureQuote` / `ScriptureRef`, which add the quotation marks and the "— KJV, excerpt" label. The website quotes the KJV (`TRANSLATION` in `server/scripture.ts`), and `bibleLink()` there gives every bible.com link in the KJV.
- **The site always reads as ready to order** (owner's decision). There is no release status: no sentence, label or notice anywhere says ordering isn't open, a piece is in preview or a release is coming soon. A piece's `availability` is `available`, `partial` (some sizes sold out) or `sold_out`, and unpublished pieces count as `available`. Cards, the home page's piece and the product page say only “Sold out” or “Some sizes sold out” (`pieceStatus`) and show the base price with no “From” (`priceLabel`, `features/catalog/query.ts`); the product page notes a 2XL/3XL upcharge under the sizes once one is chosen. Customer-facing copy never names the supplier: “our print and fulfillment partner”, “our checkout partner”.
- **Internal codes**: `code` stays in data (SKUs, records) but is never rendered, searched or put in metadata. Structured data and `llms.txt` carry no SKU for the same reason.
- **Metadata**: an indexable page exports `pageMeta({ path, title, description })` from `lib/site.ts`, which sets the canonical address and the whole share card (a page's `openGraph` replaces the layout's). Shop views build their address with `shopCanonical`, which the sitemap shares. Structured data goes through `<JsonLd>`. Only confirmed facts: no offer for a preview, no shipping or return details until they are confirmed, Scripture by reference only in `llms.txt`. A new indexable page goes in `server/indexable.ts`, so the sitemap lists it and IndexNow sends it.
- **Guides are unlisted** (owner's decision): the pages under `/christian-apparel` are never linked from the header, footer, shop, home or product pages. They stay in the sitemap and `llms.txt` and link to each other. Every visitor and crawler gets the same page: never gate them by user agent, which search engines treat as cloaking. Their copy runs the brand voice and de-AI-ify checks, names pieces only where it must, and takes prices, Scripture, art and fabric from the catalog.
- **IndexNow** (`server/indexnow.ts`): `syncIndexNow()` sends only what a reader would see as new, changed or gone, so any event may call it. It runs after a production deploy (`.github/workflows/indexnow.yml`), after the owner publishes or retires Archive content, and from the daily cron. Don't render dates, counters or random text into public pages: they change the fingerprint and resend pages that didn't change.
- **Current path**: use `usePath()` (`lib/pathname.ts`), never `usePathname()` directly, for anything rendered on the server. Vercel renders the prerendered home page as `/index`; the raw value once made the footer and header differ from the browser's render (a hydration error in production only).
- **Bag**: `useBag` (zustand, persisted to localStorage, rehydrated after mount). The `validateBag` action re-prices it whenever it's shown; never trust client prices. `startCheckout` answers `{ url }` and the browser goes to Fourthwall's hosted checkout. Every in-stock line is in the subtotal and goes to checkout. A bag holding a piece that isn't published in Fourthwall yet can't check out: `startCheckout` refuses it with “Checkout isn’t available right now. Your bag is saved, so please try again a little later.” and the bag stays as it is. A piece's SKUs change when it goes from preview to on sale (they become Fourthwall's variant ids), so each line is sent with its piece, color and size (`toLineInput`) and `CatalogIndex.findVariants` finds it again: a saved selection survives publishing. A line that matches nothing is removed with a notice.
- **Auth**: Supabase via `@supabase/ssr`. Passwordless only (Google OAuth, email link or 6-digit code). Everything degrades to "Accounts open soon" when `NEXT_PUBLIC_SUPABASE_*` is unset. Server code takes the user from `server/session.ts` (`currentUser`, `requireUser`, `requireAdmin`; `sessionUserId` for pages that only personalize a link). After the email code is accepted, the form loads the destination in full: a client navigation could reuse a prefetch made while signed out, which the proxy answered with a redirect to sign-in.
- **Analytics** (PostHog): every custom event is declared in `lib/analytics-events.json` (a JSON Schema: name, description, typed properties) and sent with `track()` from `lib/analytics.ts`, never with `posthog-js` directly. Add an event to the schema first (typecheck then holds every call to it), and register it in PostHog (Data management → Events) with the same description. Properties carry slugs, counts and choices, never an email, a name, an address or other personal details, and nothing typed except the shop search (`shop_filtered.search`, named on the Privacy page); PostHog knows a signed-in shopper only by the Supabase user id (`identify`). Session replay stays off. A change to what is collected changes the Privacy page too.
- **My Archive**: two serializers, two responses. Public pages (product pages are cached) read only `getPublishedPublicCard`; account pages and the `/api/archive/*` handlers are dynamic, check `getEntitlement` per request and answer `Cache-Control: private, no-store`. Draft content, storage paths, order rows and anything about another account never reach a public page or a Client Component prop. Every benefit claim is worded once in `features/archive/offer.ts` and shown only when the public offer allows it (`getArchiveOffer()` in `server/archive/offer.ts`, built from `getArchiveReadiness()` and cached for a minute), so nothing is advertised before it works; public pages and Client Component props get booleans, published public fields and wallpaper kinds, never ids or paths. The product page's note asks after mount whether the shopper owns the design (`designAccessAction`, a yes or no). New Archive tables are server-only; read and write them through `supabaseAdmin` after the session check. Owner pages live under `/account/admin` and need the `admin` role (`user_roles`, granted from the command line). **Idea Submissions** (`shared/ideas.ts` holds the rules: 5 purchases open the first, every 3 more another; a purchase is one paid, linked order not refunded in full) are checked on the server at upload and again at submit; the owner always has the form, and an owner-only switch shows the locked tile and page as a customer sees them.
- **Styling**: brand classes (`.aw-*`) for type and components, Tailwind utilities for layout, tokens for every color. No raw hex. Garment swatches go through `colorCss(color)` from `@/shared`: the brand token when the color is known, otherwise Fourthwall's swatch hex (product data, not styling). Fonts are self-hosted from `@fontsource-variable/*` via `next/font/local` (no Google Fonts requests).
- **Motion**: Motion is one idea: the garment image travels between a tile and its product page (view transitions), and pages cross-fade. Nothing animates on load or on scroll; the one exception is the home page's opening plate, where the pieces take turns while it is on screen: the plate cross-fades, and the garment fades out before the next fades in, so two never show at once. It pauses on its buttons, its garment and the lead piece below (which follows it), on focus and with its Pause button, and holds still with reduced motion, where every change is instant. Artwork, Scripture and buttons are whole and readable in every frame: never cropped, wiped or faded in. Reduced motion gets instant navigation. The morph is React's `<ViewTransition name={"piece-" + slug}>` around a tile's listing image and the product stage's first frame: both ends show the same picture (`1.webp`), and a name appears once per page (the home hero shows a different picture, so it is unnamed; a product page's wall leaves out its own piece). Neighbour links pass `transitionTypes`. Product pages are cached (`revalidate` plus an empty `generateStaticParams`) so the destination is ready. Anchors land below the header (`scroll-margin-top` on every `[id]`).
- **No labels above headings** on any page (no `.aw-label` over an `h1`–`h3`, no “Latest drop · Release 01” strings, no status chips). Context goes in the heading or a plain sentence. Product cards put the name first for the same reason. Form labels (Color, Size, Collection) stay.
- **Plates**: a piece's `plate` (`{ token, ink, swatch? }`) names its `--plate-*` token and the ink (bone or coal) its lettering takes. A plate imported with a token the brand tokens don't have yet carries `swatch`, its surface color read from `plate-wide.webp`; `plateCss` falls back to it (`var(--plate-x, #…)`), so a new piece shows its own surface without a code change. Add the token to `tokens.css` and `PLATE_HEX` when convenient. `.aw-plate` (brand package) sets the field; only large lettering, filled buttons and images go inside it. A piece without a plate falls back to its listing image on coal.
- **React 19 lint rules**: don't call setState synchronously in effects. Adjust state during render when a prop changes (see `product-grid.tsx`, `site-header.tsx`).
- **The product stage** (`features/product/product-gallery.tsx`): on desktop the images fill the left of the page from the header down and stay put while the buy column scrolls; the column is never wider than 1.05 times its height, so a 4:5 image that covers it loses only background and always shows the whole garment. Thumbnails sit in a strip under it, never over the garment. Hovering with a mouse zooms the image 2× around the pointer; on touch, pressing and holding for 180 ms zooms and dragging looks around, while a quick swipe still changes images. Lifting the finger or leaving the image zooms back out. Tiles and cards don't zoom.
- **Images**: product images are plain `<img>`. Each piece's close-up, cut-out and plate images are addressed through `product.media` (`detail`, `piece`, `plateWide`, `plateTall`), never built from the slug: Behold's point at `public/products/<slug>/`, a piece imported from a zip at the public `product-images` bucket (`<slug>/<name>-<hash>.webp`, named after their content so a replaced image is a new address; size guides under `size-guides/`). What follows describes Behold's files. `public/products/<slug>/` holds the site's product images, made by `assets/mockups/fourthwall.py` and `compose.py` from each product's image list in Fourthwall, in the same order: `1.webp` (the listing image), `2.webp` (hover), and so on; four for tees and hoodies, three for caps. Finished photos are cropped to 4:5 (only photos whose background matches the piece's surface; `compose.py` reports any that don't), a photo framed tighter than the rest (a `frame` in `fourthwall.json`; By His Hem's listing photo since October 17, 2026) is zoomed out to the set's scale by `widen.py`, and Fourthwall's cut-out renders are placed on the piece's own surface. Cards get every image's address as `gallery`: on touch screens the card's image is a strip to swipe through them (`ProductCard` in `packages/brand`). After a product's images change in Fourthwall, `fourthwall.py --sync <piece>` refreshes its list and downloads it (it reads `FOURTHWALL_STOREFRONT_TOKEN` from `.env.local`), then `compose.py <piece>` rebuilds only that piece. A product not in `assets/mockups/fourthwall.json` falls back to its mockup (`front`/`back`/`side.webp`). Beside them, built from the slug and never listed in `images` in `catalog.json`: `detail.webp`, a close-up of the piece's artwork cropped from its Fourthwall render (640×800, the whole print, never enlarged, and never reaching past the garment's edge: `compose.py` prints any crop that does), shown on the home page and in the product page's design story; and the plate: `plate-wide.webp` and `plate-tall.webp` (the surface alone, lit where the garment sits) and `piece.webp` (the garment cut from the shop's first photo with its own shadow by `assets/mockups/photo_cutout.py`, so the home page's opening plate shows exactly what the shop leads with). Every piece needs all four. These images are used for previews and live products alike; Fourthwall's own photos are only a fallback (`catalog-merge.ts`). The founder portrait is `public/about/richard-{480,960}.webp`; its captions and alt text name Richard and nothing he is wearing, and it is never presented as a photo of a product.
- **Addresses**: build a piece's links with `pieceHref(slug)` and its owned card's with `collectionHref(slug)` (`src/shared/catalog.ts`), never by hand. A piece renamed after launch keeps its slug, which keys its Archive rows, saved hearts, orders and `public/products/<slug>/`, and gets a new address: Fear Not (The Passage until October 15, 2026) keeps the slug `the-passage` and lives at `/shop/fear-not`; the old address answers with a permanent redirect; its Fourthwall link is `fear-not-hoodie`. The catalog's name wins over the name stored in `archive_designs` (`server/archive/designs.ts`), so a rename shows before the row is refreshed. Each design's Fourthwall offer id is pinned in `archive_designs`, so orders still match a design after its Fourthwall link changes.
- **A new release** needs no code: Admin → Collections → New collection (or "Create this collection" from a zip's `collection.json`), then Admin → Pieces → Import a piece zip, one per garment (the awebound-new-piece skill's `<slug>-package.zip`: piece.json, content.json, images, wallpapers, optional collection.json, size-guide.json and .png; print/ and previews/ are left out in the browser). The import checks the schemas, uniqueness of slug, code, Fourthwall slug and offer id, the required files, image sizes (gallery 1000×1250, plates 1600×900 and 900×1400, wallpapers 1290×2796 and 3840×2160; a wrong aspect ratio is flagged) and that no customer-facing text names the supplier or an internal code, then creates everything as drafts: the piece and its images, the Archive draft (`insertDraft`), the wallpapers (`ingestAsset`), the size guide and the offer id (`mapOffer`). The piece's review page shows everything a customer meets, editable, one step per tab in the order customers meet it (Shop card, Product page, Size guide, Home and plates, My Archive, Wallpapers, Fourthwall, Publish; `?tab=`), with Preview as customer; Approve & publish needs a name, category, a price ($0 allowed), four gallery images, Scripture with KJV text, a size guide and a Fourthwall product (looked up through the Platform API, `server/archive/fourthwall-platform.ts`, which sees hidden and archived products; an archived one offers the live product with the same slug), and warns about wallpapers, Archive copy and a Fourthwall product out of step with the site. **Fourthwall follows the admin** (`server/catalog-admin/fourthwall-sync.ts`): a piece shoppers can see has its product PUBLIC, every other piece's is HIDDEN. Publishing (a piece in a live release, or a release) makes the products public first and changes nothing if Fourthwall refuses; unpublishing a piece or a release, and deleting a draft, hides them (never archives); each change refreshes the `fourthwall-catalog` tag. The Fourthwall tab and the Pieces list show where each product stands, with one-click fixes (link the live product, match the site, take Fourthwall's prices). Prices, names and descriptions are set in Fourthwall: its API can't change them. In a published release the piece goes live at once; in a draft release it waits and goes live with Publish collection (`catalog_publish_collection`), which dates the release today unless it has a date, so it becomes Latest Drop. Latest Drop, the home page, Collections and the shop selector pick it up. The home page opens on the release's first `featured: true` piece in release order (or its first piece). A release name with a character missing from `WIDTHS` in `components/fit-name.tsx` sets a little short; add the character's width.
- **Size guides**: the `size_guides` table (seeded from `sizeGuides` in `catalog.json`; new ones arrive in a zip and are edited on a piece's review page) holds each blank's measurements exactly as the owner's guide image prints them (fractions as text, one value per `measures` column), its fit line, an optional sizing note (shown in the guide and under the size buttons; none today) and the image (`public/size-guides/*.webp`, made at 1600 px wide from the PNGs in `assets/size-guides/`; the Organic Oversized PNG has the owner's “US sizing note” box cut out). A product's `sizeGuide` picks its guide, and the guide's sizes are the sizes a preview offers. `blank` (supplier and Fourthwall id) never leaves the server. The sheet widens to 560 px for the image; the measurements also render as a table for screen readers. A guide without an image shows the table.
- **Returns copy** mirrors Fourthwall's return policy and lives in four places that must agree: `app/refunds/page.tsx` (the full policy), the FAQ's Returns and refunds answers, `features/product/delivery-summary.tsx` and `app/llms.txt/route.ts`. The reporting window is `DELIVERY.problemWindowDays`.
- **Previews** (internal only): a content entry with no published Fourthwall product carries `preview: true` (content price and `sizePriceCents`, the size guide's sizes and the site's images; SKUs like `A3-B01-FADED-BLACK-M`). The site shows it exactly like a piece on sale; only `startCheckout` and structured data (no offer) treat it differently.

No tests (owner's instruction). Verify by building and walking the flows in a browser on desktop and a phone width, with and without reduced motion: the home page's pieces taking turns (and holding still with reduced motion), its two buttons, the lead piece and the wall → the category select (and collection, once there are two releases) → product (a tile's image should travel into the stage; the next and previous pieces slide in) → Add to bag, from the button and from the phone bar (choose 2XL or 3XL to see the price note) → checkout (lands on Fourthwall once the products are published; until then the try-again message); notify; contact; sign-in; and My Archive's discovery surfaces signed out, signed in and as an owner (the steps are in docs/ARCHIVE.md, "Discovery"). Check that lettering fits at 320px and that nothing but lettering, buttons and images sits on a plate. Check error messages with `pnpm build && pnpm start` too: `next dev` shows thrown messages that production hides.
